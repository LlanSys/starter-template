# Secure workspace onboarding

Customer workspaces start pending KYC. A platform operator with `control_plane.manage` and `control_plane.approve_kyc` records the approval and its evidence reference. A pooled workspace can activate after approval. Isolated workspaces wait for the provisioning callback. A failed provisioning retry and reactivation require existing KYC approval. The reserved platform and Demo workspaces follow their own initialization paths.

For an upgraded active customer, record the actual review in the tenant listing before issuing a first-administrator invitation. The additive migrations preserve existing credentials, roles, and tenant states. Existing approvals are represented as awaiting review until evidence is recorded. An operator can reissue a legacy invitation from Workspace setup. The ordinary IAM invitation cannot set the password of the initial administrator associated with an older workspace.

The create-tenant form can record an optional initial administrator. Control Plane saves that invitation intent with the workspace in one transaction. After KYC and provisioning, the delivery worker prepares the tenant-owned role and essential entitlements before sending the welcome link. Operators can also enter the initial administrator in Workspace setup. The durable worker leases delivery in Control Plane, issues a random credential, and stores only its hash. An unsuccessful delivery retries with backoff. Resend invalidates old credentials. Revoke prevents acceptance and unfinished setup. Operators can issue a fresh link for the same invited administrator. Viewing the welcome page only displays information. An explicit acceptance creates a restricted IAM identity or verifies the invited existing account using its established credential. Finishing setup requires a verified application authenticator challenge after enrollment. A signed proof for that session survives refresh. The role is granted through StarterTemplate IAM after the invitation and workspace are checked again.

## External sign-in

Set the API `ExternalSignIn:PublicApiOrigin` to the central API origin visible to the browser and configure each approved Blazor origin in `ExternalSignIn:ClientOrigins`. Configure the Blazor `BackendApi:PublicBaseUrl` to the same public API origin. Keep `BackendApi:BaseUrl` as the server-to-server address. Configure only the providers you intend to expose.

- Microsoft uses `EntraId:Enabled`, `TenantId`, `ClientId`, and `ClientSecret`. Register the exact public API callback at `/signin-oidc` by default.
- Google uses `GoogleSso:Enabled`, `ClientId`, and `ClientSecret`. Register the exact public API callback at `/signin-google` by default. Use a Web application client and allow your account as a test user if Google consent is in testing.
- Keep provider credentials in user-secrets for local runs and in your environment's secret store for deployments. The callback registrations, enabled provider credentials, and approved origins must match the actual environment.

The app binds validated issuer and subject together and binds the sign-in to the selected workspace. It never links by email. Local accounts can connect a provider from Account security using current-password confirmation and a short-lived one-use ticket. Older Microsoft mappings may contain only the subject. Reconnect those accounts or perform an issuer-verified migration. External sign-in challenges the app authenticator for enrolled accounts. A Google invitation additionally requires a verified email matching the invited address.

Apply the StarterTemplate IAM and Control Plane onboarding migrations and the Shared outbox compatibility migration for your database provider. The Shared migration adds the indexes expected by MassTransit 8 and retains queued state and legacy bus metadata. Use fresh and upgrade databases. Live Microsoft and Google consent require registered provider applications and their actual callbacks.
